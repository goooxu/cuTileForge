# 第十五阶段：把纯度上限提到 0.3 是个错误，以及速度那条路通了

两个结果，一个否定一个肯定：

1. **纯度上限提到 0.3 适得其反。** pass@1 涨到 55.8%（历史最高），但解出题数从 150 掉到
   **147**，而且**它瞄准的那个 bucket 反而变大了**——Level 2 的纯度失败从 25 道涨到 31 道。
   失败机制正是我在代码注释里预先标注的那一个。
2. **速度是探索问题，不是知识缺口。** 高温采样下，模型在同一道题上写出的 kernel 速度差
   最高到 1.8x，而且会主动改 tile size。这条路是通的，只是常规温度掩盖了变异。

**M（150/200）仍然是最好的模型。**

## 1. 纯度上限：假设、做法、结果

第十四阶段把纯度失败从恒定 0.0 改成 0.04-0.18 分级，Level 1 的纯度失败清零了，
但 **Level 2 仍有 25 道**、占比 75% → 71% 几乎没动。当时的猜测是**上限压得太低**：
0.18 对"编译不过"的 0.20，"差一个激活"和"根本跑不起来"几乎无差别，拉力不够。

于是这一轮把"数值已正确"的纯度失败单独提到 **0.20-0.30**。这需要验证器对不纯候选也跑一遍
数值检查（原来在纯度门就 `continue`）。冒烟测试确认：200 个样本里 65 个纯度失败，
39 个够格检查，**29 个数值完全正确**——目标人群确实存在且不小。

代价我当时就写进了注释：**这打破了"任何纯的尝试 ≥ 任何不纯的尝试"这个结构性保证**
（0.3 > exec 档的 0.2）。留的兜底是硬门槛（无真实 kernel、用 `torch.nn` 计算层仍然 0.0）
和组内归一化（组里只要有真 pass 的 1.0，那些 0.3 就拿负 advantage）。
标注的风险是：**在模型做不对的题上，0.3 会变成舒服的局部最优。**

### 结果：风险实现了

| | pass@1 | pass@4 | 解出 | 快过 compile |
| --- | ---: | ---: | ---: | ---: |
| L | 44.6% | 72.0% | 144/200 | 41 |
| **M** | 51.6% | **75.0%** | **150/200** | 43 |
| N | **55.8%** | 73.5% | 147/200 | 41 |

Level 2 的纯度失败：

| | 未解出 | 其中纯度失败 | 占比 |
| --- | ---: | ---: | ---: |
| M | 35 | 25 | 71% |
| N | 38 | **31** | **82%** |

**靶子变大了。** 而且 N 相对 M 在 Level 2 上丢了 11 道，**其中 9 道的失败模式正是
"数值正确但没过纯度门"**——也就是说 M 本来能写出完全纯的通过解，N 改成了"算对但留个
torch 尾巴"。

训练侧完全看不出来：纯度率 0.9706 → 0.9710 基本持平，pass 0.827 → 0.870 还在涨。
**因为训练任务的融合链比基准简单得多，纯度率已经到 0.97 的天花板，那个局部最优在训练
分布上根本不构成诱惑。** 我在中途汇报时说"纯度守住、pass 继续涨，排除了该失败模式"——
那个判断是错的，训练指标没有分辨力。

### 结论

**上限该留在 0.20 以下。** 第十四阶段的 0.18 不是"拉力不够"，而是那个不变式本身在做实事：
一旦不纯可以排在"纯但编译不过"前面，模型就会在难题上选择停下。Level 2 剩下的那 25 道
不是奖励刻度的问题，得换别的思路。

pass@1 涨的 4.2pp 是真的，但它来自已解出题上的可靠性提升，代价是 3 道净损失和目标 bucket
恶化——不划算。

## 2. 速度判定实验：通了

用 M 在 16 道稳定 8/8 解出的合成题上高温采样（T=1.2 / top_p=0.98，平时 1.0 / 0.95），
k=16，看**正确样本之间**的速度分散。判据在跑之前就写死在
[verify/speed_probe.py](../verify/speed_probe.py) 里：

| | |
| --- | --- |
| 内部差异 ≥1.3x 的题 | **8/16（50%）** |
| 内部差异 <1.2x 的题 | 6/16 |
| 中位 best/median | 1.26x |
| **用了多于一组 tile size 的题** | **9/16** |

预设门槛 1/3，实测 50%——**变异存在**。个别题差得很大：6.46x → 11.05x（1.71x）、
5.82x → 10.46x（1.80x）、1.65x → 2.85x（1.73x）。1 号题在样本间用过
`TILE_SIZE=2048` 和 `TILE_SIZE=256` 两种。

对比 dev 上常规温度的读数（4/4 全对的题里，Level 1 只有 3/39、Level 2 只有 0/15 有
≥1.3x 差异），说明**不是模型只会一种实现，是温度把变异压掉了**。

所以速度是**探索问题**。可行的下一步很具体：在模型已经稳定解出的题上、用更高的 rollout
温度、只按速度给 group-relative advantage。而那批题正是 `select_frontier.py` 现在当作
"无梯度"丢掉的（M 的筛选里有 326 道"次次答对"被扣掉）——**素材一直都在，只是被扔了。**

## 3. 下一步

1. **把纯度上限退回 0.18**（保住不变式），N 的 adapter 保留但不作为主线。
2. **speed-only RL**：frontier 改成"稳定解出"的题，rollout 温度提到 1.2，reward 只按速度
   归一化。这是目前唯一有实验支撑的、还没吃过的方向。
3. **Level 2 那 25 道纯度失败**换思路。奖励刻度已经试过两个方向（0.0 → 0.18 有效、
   0.18 → 0.30 有害），说明瓶颈不在刻度。
4. 中位加速对 `torch.compile` 仍是 0.92x。

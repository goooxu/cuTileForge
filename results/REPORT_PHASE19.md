# 第十九阶段：三件事——评测口径、inductor 的弱项、以及第一次真正推动纯度那一块

## 1. 修复反馈：加一句"你的数值本来就是对的"，修复率翻六倍

`repair/prompts.py` 原来对纯度失败只说"没有完全用 cuTile 实现"，**没有告诉模型它的数值
已经验证通过了**。所以模型没有理由相信自己的 kernel 是好的，倾向于整个重写——顺手把
本来对的部分也写坏。

现在验证器会对不纯候选跑数值检查（第十四阶段加的 `impure_correct`），于是可以说清楚：

> 你的 kernel 算出了正确的数值，所以计算本身是对的。它被拒只是因为一部分工作还由 PyTorch
> 完成而不是 cuTile：`Uses torch computation op: torch.relu`
>
> 把剩下的算子搬进 cuTile kernel，其余一律不要改。

单次修复尝试的成功率：

| | 第九阶段（通用反馈） | 本轮（定向反馈） |
| --- | ---: | ---: |
| Level 1 / 86 | 2.2% | **12.1%** |
| Level 2 / 87 | 2.9% | **18.8%** |

**约六倍。** 两次采集（86 和 87 各 4 个样本、2 轮修复）里，修复轮额外产出 **317 个
一次生成拿不到的 kernel**。

这和第九阶段撤回的结论不冲突，区别要说清楚：**撤回的是把修复循环当推理时手段**
（等预算下不如重采）；**当数据采集器**是第三、四阶段验证过有效的，本轮是后者。
纯度失败也恰好是反馈信息量最高的场景——不是"自己找哪里错了"，而是"这一个具体算子没搬"。

## 2. 训练结果：靶子第一次动了，但总分没超过 M

用修复产出的 kernel 训 model R（2,346 条 / 1,191 道任务，从 merged M 继续）：

| | pass@1 | pass@4 | 解出（k=4） | 快过 compile | 中位 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **M** | 51.6% | **75.0%** | **150/200** | 43 | 0.92x |
| Q（第二次自蒸馏） | **54.2%** | 70.5% | 141/200 | 43 | 0.94x |
| R（修复数据） | 53.8% | 72.5% | 145/200 | 42 | 0.94x |

**但瞄准的那一块确实动了**，这是三轮尝试以来第一次：

| Level 2 未解出题中"数值正确但没过纯度门" | |
| --- | ---: |
| M | 25/35（**71%**） |
| **R** | **18/36（50%）** |

第十四阶段把 Level 1 的纯度失败清零了但 Level 2 没动；第十五阶段提高奖励上限反而让它涨到
82%；这一轮**从 25 道降到 18 道、占比从 71% 降到 50%**。机制是对的。

代价在别处：Level 1 的未解出从 15 涨到 19，卷积的"能跑但数值错"从 8 涨到 11——
R 把一部分纯度失败转成了数值失败。净账 150 → 145。

## 3. 第四轮同一形态

| 轮 | 干预 | pass@1 | 解出（k=4） |
| --- | --- | ---: | ---: |
| 十四 | 纯度分级 + 链尾任务 | 51.6% | **150** |
| 十五 | 纯度上限 0.3 | 55.8% | 147 |
| 十六 | 速度目标 | 52.4% | 147 |
| 十七 | 第二次自蒸馏 | 54.2% | 141 |
| 十九 | 修复数据 | 53.8% | 145 |

**M 的 150 已经四轮没被超过，而每一轮的 pass@1 都比它高。** 这不再像是四次独立的失误，
而是同一件事：**k=4 的"解出题数"在这个方法体系下已经饱和**，任何进一步的训练都在把概率
质量集中到已经会做的写法上，代价是少数派里那个偶然正确的解。

## 4. 评测口径：建议改

十九轮里"解出题数（k=4）"一直是头条，但那是从最早继承下来的惯例，没有论证过。
Q 在 k=16 上解出 **163/200**，而 M 在 k=4 上是 150/200——如果实际使用会采多次
（工程上很自然：验证器就在手边，采四次挑一个能过的），那 163 比 150 更有意义。

**建议**：头条改成 **pass@1 + pass@k 曲线**，而不是单一的 k=4 解出数。理由：

- pass@1 是单次生成的真实体验，无歧义
- 曲线暴露可靠性与覆盖面的权衡，而单点会把它藏起来——上面那张表里五轮的 pass@1 都在涨，
  单看 k=4 却像是全在退步
- k=4 这个具体数字没有任何特殊性

代价是历史数字要重新表述，而 M 之前的模型大多只采过 k=4，pass@16 补不上。所以我建议
**并列报 pass@1 和 k=4，并对新模型补 k=16**，而不是追溯重算。

## 5. inductor 的弱项：速度目标的精确定位

第十六阶段的教训是"任务池里没有需要的速度区间"。这次换个问法：**对手在哪里弱？**
`torch.compile` 相对 eager 提速不到 1.05x 的题，是 inductor 帮不上忙的题。

| | 解出 | 中位加速 | 我们快过 compile 的 |
| --- | ---: | ---: | ---: |
| inductor 帮上忙的（74 道） | 52 | **0.761x** | **3** |
| inductor 帮不上忙的（125 道） | 98 | **0.994x** | **40** |

**结论很干净：inductor 用不上的地方我们基本追平（0.994x），inductor 一发力我们就输
（0.761x，52 道里只赢 3 道）。** 我们的 kernel 大致做到了 eager 语义允许的水平，
但打不过融合。

不过"inductor 平"这个代理**会把两种完全不同的情况混在一起**：一种是没有强库也没有融合
空间（真机会），另一种是 cuBLAS/cuDNN 已经吃掉了（最难）。矩阵乘属于后者——eager 和
compile 都调 cuBLAS，比值当然是 1.0，但绝对门槛极高（我们在 0.007-0.073x）。

**剔掉 matmul/conv 之后剩 31 道，才是够得着的**：

| | 数量 |
| --- | ---: |
| 类别 | activation 19、other 7、reduction 3、norm 2 |
| 我们的加速比 ≥0.8x | 7 |
| 0.5-0.8x | 9 |
| <0.5x | 15 |

最有价值的一组是**纯逐点激活**：`27_SELU_`、`31_ELU`、`32_HardTanh` 都是参考 1.82ms、
我们 0.556x（约 3.3ms）。**逐点算子是带宽受限的，门槛只是"一个写得好的单 kernel"**，
0.556x 说明我们有大约 2 倍的效率损失——很可能是 tile 尺寸导致的访存不合并或向量化缺失。
而第十五阶段的探针恰好显示 tile 尺寸在样本间会变（2048 / 256）、最好对中位能到 1.4-1.8x。

**所以速度的下一个靶子是明确的**：大张量逐点激活，1.82ms 量级的参考，我们在 0.556x，
奖励项在这个区间是有梯度的（0.55x → −0.13，没有钳位）。这比"筛慢的题"精确得多。

## 6. 下一步

1. **造大张量逐点激活任务**，让速度奖励在 0.5-1.0x 这个有梯度的区间工作。这是速度那条路
   第一次有精确定位的靶子。
2. **改评测口径**（见第 4 节），否则后续每一轮都会看起来像退步。
3. **k=4 的解出数已饱和**：想再涨得靠扩覆盖面，而这四轮证明锐化不行。修复循环是唯一
   真正产出"模型本来写不出的解"的机制（317 个），值得继续用作数据源。
4. 第二套封存题集（770 道）还没开封，留给下一次需要独立验证的时候。

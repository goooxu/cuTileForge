# 第十二阶段：给"数值错"分级，以及一个把我带偏的诊断 bug

**结论先说**：把"能跑但数值错"从恒定 0.6 改成按相对偏差分级，dev 200 从 134 道涨到
**144 道**，快过 torch 的从 49 涨到 **60**。而且它**几乎不需要策略漂移**换来这些——
KL 是 K 的 1/54。

| | pass@1 | pass@4 | 解出 | 快过 torch | 中位加速 | 训练末段 KL |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 基座 | 12.9% | 23.5% | 47/200 | 5 | 0.12x | — |
| H（起点） | 28.5% | 54.0% | 108/200 | 38 | 0.95x | — |
| K（恒定 0.6） | 42.8% | 67.0% | 134/200 | 49 | 1.00x | 0.5522 |
| **L（分级）** | **44.6%** | **72.0%** | **144/200** | **60** | 1.00x | **0.0102** |

K 和 L **起点相同（model H）、frontier 相同（575 道）、超参完全相同**，唯一差别是
reward 在这个带里的形状。

## 1. 先说那个 bug，因为它差点让整条路线押错

诊断 K 的失败时我用了 `compiled and not numerically_correct` 判定"能跑但数值错"。
`analyze_cutile_run.py` 自己的注释就写着为什么不能这么做：

> KernelBench's `compiled` only means the module imported; @ct.kernel does not
> compile eagerly, so tileiras actually runs at first launch.

**cuTile 是首次 launch 才 JIT 编译的，所以编译失败的 kernel 照样 `compiled=True`。**
我那个判据把所有 cuTile 编译错误都算成了数值错，于是报出"92.4% 的未解出题是数值错"。

用正确的 `failure_stage` 重算，K 的 66 道未解出题是：

| | 数量 | 占比 |
| --- | ---: | ---: |
| **数值正确但没过纯度门** | **34** | **51.5%** |
| 能跑但数值错 | 22 | 33.3% |
| cuTile API 误用 | 8 | 12.1% |
| 其他 | 2 | 3.0% |

**最大的一块根本不是数值，是纯度。** 教训很直接：一个判据用错，把最大的靶子藏了起来，
还顺手造出一个假的。`train/diagnose_regression.py` 现在用 `failure_stage`，
并在注释里写明为什么不能用 `compiled` 重建它。

## 2. 分级 reward 本身仍然成立

好在这个 bug 不影响本轮的改动：`rl/reward.py` 判定"数值错"走的是**验证器的错误文本匹配**
（`output mismatch` / `non-finite`），认的是真正的数值不匹配，不看 `compiled`。

原来的问题是真的：这一档给恒定 **0.6**，从"最后一位不同"到"差六个数量级"同分。
对 GRPO 尤其糟——组内八个样本全落在这一档时 advantage 精确为零，整组白跑。

验证器其实早就算出了偏差（`allclose` 失败时打印 max diff），但只写在错误文本里。
现在记成结构化字段，按参考输出量级归一化，reward 在带内按对数刻度插值：

| 相对偏差 | reward |
| --- | ---: |
| ≤1e-4（刚出容差） | 0.600 |
| 1e-3 | 0.525 |
| 1e-2 | 0.450 |
| 1e-1 | 0.375 |
| ≥1.0 | 0.300 |

下限 0.3 仍高于"纯 cuTile 但编译不过"的 0.2，档位序关系不变。

## 3. 最值得注意的不是 +10 道，是 KL

| | K | L |
| --- | ---: | ---: |
| reward 前半 → 后半 | 0.652 → 0.740 | 0.622 → 0.730 |
| pass 前半 → 后半 | 0.500 → 0.632 | 0.501 → 0.650 |
| **末段 KL** | **0.5522** | **0.0102** |

两者到达几乎相同的训练 reward 和 pass，但 **K 是靠离开起点 54 倍的距离换来的**。

这给了第十一阶段那个"KL 漂了 70 倍"一个解释：**当组内没有真实的接近度排序时，
策略只能靠大幅偏移去撞运气**；给了带内梯度之后，同样的收益可以在起点附近拿到。
K 那些类别退步（矩阵乘 13 → 11）大概就是漂移的代价——L 把矩阵乘拿回到 13，
和起点 H 持平。

按类别：卷积 74 → **77**（快过 torch 的 35 → **40**），归一化 11 → **18**，
矩阵乘 11 → **13**。退的是归约（7 → 5）和池化（2 → 1）。

## 4. 下一个靶子已经明确

L 剩下 56 道未解出题：

| | Level 1 | Level 2 | 合计 |
| --- | ---: | ---: | ---: |
| **数值正确但没过纯度门** | 2 | **27（75%）** | **29（52%）** |
| 能跑但数值错 | 9 | 9 | 18 |
| cuTile API 误用 | 7 | 0 | 7 |

**纯度仍是最大的一块。** 看 K 上被挡的 73 个样本的原因就知道是什么在挡：

| 次数 | 被挡原因 |
| ---: | --- |
| 17 | 用了 `torch.relu` |
| 12 | 用了 `torch.softmax` |
| 11 | 用了 `torch.sigmoid` |
| 9 | 用了 `torch.logsumexp` |
| 8 | 用了 `F.gelu` |
| 6 | 用了 `torch.tanh` |

**全是逐点激活。** 模型把难的部分（卷积、GEMM、归一化）成功搬进 cuTile，然后在链尾
顺手写个 `torch.relu(...)` 交卷。Level 2 全是融合链、链尾几乎都是激活，所以这里最严重。

这也解释了激活族为什么一直"退步"——它从来没稳过，**模型在链条语境里不会用 cuTile 写激活**。
第十一阶段补的激活 builder 是**独立单算子**任务，没补到"链尾激活"这个语境。

`rl/reward.py` 给纯度失败 **0.0**，和空白卷同分。一个数值完全正确、只差最后一个
`torch.relu` 没搬的解，拿到的信号和什么都没写一样多。当初设 0.0 是防 reward hacking
（把活儿甩回 PyTorch 是刷正确率最省力的路），顾虑是对的，但一刀切掐掉了唯一指向正确
方向的梯度。

## 5. 下一步

1. **按"还剩多少 torch"给纯度失败分级**，硬门槛是"代码里必须真有被 launch 的
   `ct.kernel`"——纯 torch 直通仍然 0.0，这样不会让甩回 torch 变划算。目标是那 29 道。
2. **造"链尾激活"任务**：现有的激活 builder 是独立算子，缺的是"前面已经是 cuTile、
   尾巴也必须是 cuTile"的融合形态。
3. **池化和损失仍然没解决**（各 5 道未解出），而且 L 上它们主要卡在 **cuTile API 误用**
   而不是数值——和其他族的瓶颈不同，需要单独看。
4. pass@1 44.6% 对 pass@4 72.0%，还有 27pp。

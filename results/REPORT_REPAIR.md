# 第三阶段：多轮编译反馈修复循环

**结论先说**：卷积的"冷启动"不存在——它是**我自己验证器的一个 bug**。修掉之后，卷积
单轮就有 8.8% 通过，修复循环再把它推到 **25.6%**（120 道卷积题里 81 道拿到正样本）。
整体从 23.6% 涨到 **42.7%**。

## 1. 决定性发现：验证器的随机种子 bug

第二阶段的核心结论是"卷积造不出数据，263 个样本零通过"，并据此判断存在冷启动问题。
**这个结论是错的。**

`verify/worker.py` 构造两个模型时只设了一次种子：

```python
set_seed(0)
ref_model = Model(*init_inputs).cuda()      # 消耗了 RNG 状态
new_model = ModelNew(*init_inputs).cuda()   # 拿到的是不同的随机权重
```

KernelBench 自己的 `eval_kernel_against_ref` 是在**每次构造模型前**都重设种子
（eval.py 第 503 行和第 566 行）。少了第二次 `set_seed`，参考模型建 `nn.Conv2d` 时
把 RNG 推进了，`ModelNew` 于是拿到另一组权重——**只要任务里的模块自带可学习参数，
数值就永远对不上，kernel 写得再对也判失败**。

这解释了第二阶段所有反常的类别分布：

| 类别 | 自带参数？ | 修 bug 前 | 修 bug 后 |
| --- | --- | ---: | ---: |
| Conv2d / PointwiseConv | 有（weight） | 0.0% | **8.8%** |
| GroupNorm | 有（affine） | 3.1% | — |
| Matmul / Softmax / 逐元素 | 无 | 41–100% | 不变 |

不是模型不会写卷积，是**验证器认不出写对的卷积**。而拒绝采样又只把验证器认可的样本
喂给训练，所以第二阶段的 SFT 数据里卷积恰好是 0 条——冷启动是自己造成的。

发现路径：修复循环跑完后卷积仍是 0/480，我去看那 853 个"编译通过但数值不对"的样本，
中位误差 1.78、没有一个进到 1e-2 以内——**误差大到不像算错，像在跟一个无关的东西比**。
翻开一个 tier-2 的 Conv2d，`ModelNew.__init__` 里自己 `torch.randn` 建了权重，而参考
模型用的是 `nn.Conv2d` 的权重。至此定位。

修完之后用 KernelBench 自己的 evaluator 交叉验证了 16 个卷积 kernel，**16/16 一致**。

## 2. 修复循环的效果

250 道合成题（卷积占 48%）× k=4 = 1000 个候选，最多 3 轮修复，全程 23.9 分钟。

### 按轮次的累计通过率

| 轮次 | 新增通过 | 累计 | 通过率 |
| --- | ---: | ---: | ---: |
| 初始 | 236 | 236 | 23.6% |
| +修复 1 | 100 | 336 | 33.6% |
| +修复 2 | 56 | 392 | 39.2% |
| +修复 3 | 35 | 427 | **42.7%** |

边际收益在衰减（100 → 56 → 35）但第 3 轮仍有正收益，说明轮次上限还没到头。

### 按类别

| 类别 | 候选数 | 初始 | 修复后 | 增量 |
| --- | ---: | ---: | ---: | ---: |
| **卷积** | 480 | 8.8% | **25.6%** | **+16.9pp** |
| 归一化 | 248 | 19.0% | 48.4% | +29.4pp |
| 池化 | 80 | 1.2% | 21.2% | +20.0pp |
| 矩阵乘 | 156 | 79.5% | 86.5% | +7.1pp |
| 逐元素 | 24 | 79.2% | 95.8% | +16.7pp |
| 归约 | 12 | 25.0% | 75.0% | +50.0pp |

**每个类别都涨**，而且原本最弱的两类（卷积、池化）涨幅最大。池化从 1.2% 到 21.2%
尤其值得注意——第二阶段它是"11 条数据、纹丝不动"的那一类。

### 卷积细节

- 123/480 候选通过，覆盖 **81 道不同的题**（共 120 道）
- 按轮次：初始 42、修复 1 拿 49、修复 2 拿 18、修复 3 拿 14
- 按难度：tier1 13、tier2 67、tier3 29、tier5 14——**不是只有最简单的能过**

## 3. 模型到底会不会改错

这是判断"真修好"还是"换了个失败方式"的关键。1970 次修复尝试的去向：

| 结果 | 次数 | 占比 |
| --- | ---: | ---: |
| 又报同一个错 | 888 | 45.1% |
| 换了个别的错 | 759 | 38.5% |
| **真的修好了** | 191 | 9.7% |
| 能编译了但数值不对 | 132 | 6.7% |

**近一半的修复尝试是原地打转**——模型收到报错后给出的新代码犯同样的错误。真正修好的
不到 10%。所以修复循环的收益不是来自"模型很会 debug"，而是来自**多给了几次带反馈的
采样机会**，在足够的样本量下积累出来。

按错误类别看修复成功率：

| 错误类别 | 遇到 | 修好 | 成功率 |
| --- | ---: | ---: | ---: |
| shape_mismatch | 44 | 7 | 15.9% |
| type_error | 517 | 66 | 12.8% |
| numeric_mismatch | 449 | 54 | 12.0% |
| rank_mismatch | 340 | 23 | 6.8% |
| invalid_argument | 140 | 7 | 5.0% |
| **grid_rank_exceeded** | 43 | 0 | **0.0%** |
| **array_used_as_tensor** | 11 | 0 | **0.0%** |

原以为规则性最强的两类（"grid 不能超过 3 维"、"Array 不能当 Tensor 用"）反而**一个
都没修好**。这两类报错信息其实已经很明确了，模型读得懂却改不对，说明它缺的不是提示
而是对应的正确写法——**正是 SFT 该补的东西**。

## 4. 产出

- **正样本池 427 个 kernel，覆盖 183 道不同的题**，其中 191 个（44.7%）来自修复轮
- 1000 条完整轨迹（含每轮代码与报错），可用于后续 agentic SFT

## 5. 判定与下一步

按预设的判定标准，落在第一行：**卷积拿到了有意义数量的正样本，冷启动破了，下一轮直接
做 SFT**。

但要修正对上一阶段的理解：卷积一直是可学的，只是被验证器挡住了。所以下一轮 SFT 的
数据构成会和第二阶段完全不同——第二阶段 409 条里卷积 0 条，这一轮光是合成任务就能拿到
123 条卷积正样本。

两个要专门处理的点：

1. **grid_rank_exceeded 和 array_used_as_tensor 修复率为 0**，且第二阶段 SFT 后
   grid_rank_exceeded 还涨了 2.1pp。这两类必须在训练数据里显式覆盖高维 idiom。
2. **第二阶段的所有合成任务通过率都要重新计算**。用修好的验证器重跑 probe_l90，
   通过率从 20.9% 变成 23.2%，此前基于旧数字的类别结论需要重新审视。

## 后记：第四阶段的实际结果

两点都兑现了，见 [../docs/WORKLOG.md](../docs/WORKLOG.md) 的第四阶段：

- 卷积在 held-out 200 题上**解出题数从 5 道涨到 14 道**（98 道卷积题）
- **grid_rank_exceeded 从 9.8% 降到 4.5%**，几乎腰斩——训练数据里 157 条卷积全是 NCHW
  四维张量，把这个 idiom 逼了出来。第三阶段"缺的不是提示而是正确写法"的判断成立
- 重验旧 run 又恢复出 38 条此前被误判的卷积正样本

有一点判断错了：本报告推断"下一轮直接做 SFT"时默认要从基座重训，实测**在第二阶段的
adapter 上续训更好**（多解出 4 道题，纯度也更高）。

## 附：环境变化

- 执行镜像基座 `nvcr.io/nvidia/pytorch:26.07-py3`，cuda-tile 仍是 1.4.0，fp32 `ct.mma`
  行为不变（smoke 测试通过），历史数字可比
- torch 2.13 里 `allow_tf32` 的语义变了：标志仍读作 `True`，但开关它已经不影响 fp32
  matmul 结果（两种情况误差都是 1.144e-4）。`enforce_reference_precision()` 照旧强制
- **vLLM nightly（0.26.1rc1）在 GB200 上不再需要任何补丁**：FlashInfer autotune 崩溃
  已修，`--enforce-eager` 可以去掉。并发 128 时 **15650 tok/s，比之前快约 60 倍**，
  `docker/Dockerfile.vllm-gb200` 已删除
- 修复循环和验证器共用 GPU，vLLM 显存占用要降到 0.55 给验证器留出空间
- 验证器 worker 现在可能被生成的 kernel 直接搞崩（CUDA context 里的非法指令，连
  `empty_cache()` 都会挂）。`VerifierPool` 改成能检测停顿、重启死掉的 worker 并重试；
  OOM 与 worker 崩溃算"不确定"而不是失败，也不会作为报错喂回给模型

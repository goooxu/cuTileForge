# 第二十阶段：速度区间对上了，但 TILE_SIZE=256 没有组内变异，所以没训

**结论先说**：第十九阶段定位的靶子是对的。造了 250 道十亿元素量级的逐点激活题之后，
model M 的中位 `best_speedup` 是 **0.614x**（对 `torch.compile`），96% 的题落在
0.4–1.0x——正是 KernelBench 上 SELU/ELU/HardTanh 的 0.556x 那个区间。第十六阶段
那种 6–11x 的错位这次没有出现。

第二道硬门没过：**只有 12% 的题 `best/median ≥ 1.3x`（门槛是 33%）**。2000 个
kernel 里 1929 个写的是 `TILE_SIZE = 256`，1995 个把张量 flatten 成 1D，**零个**
用 2D tile。这就是 prompt 里那个 vector-add 例子的数字。按计划停了，**没有跑 GRPO**。

没有新模型，所以没有共同题集上的逐题速度比，三个锚点也还是 ~0.556x。
本轮改的是评测口径：头条从「k=4 解出数」换成 **pass@1 + pass@k 曲线**。

## 1. 任务对了

KernelBench Level 1 激活是 `(4096, 393216)`，约 16 亿元素。此前速度课的 `PERF_2D`
最大 `8192×8192`，差约 24 倍。新表 `BW_2D` 在 0.8e9–1.4e9 元素，形状全部错开测试集
（没有 `(4096, 393216)`）。builder `large_pointwise_activation` 只用真正逐点的
21 个激活，softmax 族拿掉了。

level 83：250 道，种子 830020。采集 k=8、温度 1.2、concepts 档、对 compile 计时。

| | |
| --- | --- |
| 通过 | 1927 / 2000（96.4%） |
| 8/8 全过 | 192 / 250 |
| 样本中位加速 | 0.590x |
| `best_speedup` 中位 | **0.614x**（min 0.546，max 1.311） |
| 落在 (0.4, 1.0) | **239 / 250（96%）** |
| 快过 compile 的样本 | 12 |

**GATE 1 PASS。** 合成任务第一次坐在基准激活所在的速度带里。

## 2. 变异不够，而且不够的原因很具体

| | |
| --- | --- |
| 至少 3 个计时通过的题 | 250 / 250 |
| `best/median` 中位 | 1.01x |
| `best/median ≥ 1.3x` | **30 / 250（12%）** |

**GATE 2 FAIL。** 计划写过：没变异是知识缺口，GRPO 抓不住，不许靠「先训着看」绕过。

tile 字面量（2000 个 kernel）：

| | 个数 |
| --- | ---: |
| `TILE_SIZE = 256` | **1929** |
| 没有 tile 常量 | 16 |
| 其它（512 / 1024 / 4096 / 16384 / 65536 / 262144 / …） | 55 |
| 同一道题出现过两种 tile | 42 / 250 |
| flatten 成 1D | 1995 |
| 2D tile | **0** |

256 不是模型「发现」的好尺寸，是
`overlay/src/kernelbench/prompts/model_new_ex_add_cutile.py` 里写死的例子。
十亿元素时 `grid.x ≈ numel/256` 到几百万 block，这就是 0.55–0.61x 那一档。

那 30 道过了 1.3x 的题，**不是慢样本把中位拉低**。每一次，更快的都是非 256 的那个：

| 题 | 最快 tile | 最快加速 | 256 最慢 |
| --- | ---: | ---: | ---: |
| 75 | 1024 | **1.082x** | 0.583x |
| 100 | 1024 | **1.013x** | 0.549x |
| 87 | 16384 | **1.139x** | 0.630x |
| 169 | 512 | **1.089x** | 0.615x |
| 118 | 262144 | **1.084x** | 0.632x |

更大的 1D tile 能把同一道题从 ~0.56x 推到 ~1.0x。更快的 kernel 模型会写，只是
八次里几乎不写。组相对优势在 88% 的题上是零——那 88% 的八个样本全是 256。

第十五阶段探针里 2048 vs 256 的变异，是在 `8192×8192` 上看到的。换到十亿元素之后，
策略收回到例子里的 256，2D tile 一次都没出现。访存合并那条假设这一轮**测不到**：
模型没写出那种 kernel。

## 3. 为什么仍然不训

solid + `0.25 < best < 1.0` 能筛出 186 道，看起来像一个速度 frontier。但其中只有
约 30 道组内有速度梯度。拿 186 道去跑 GRPO，等于在 80% 的 rollout 上对相同的
`TILE_SIZE=256` 做组归一化，advantage 是噪声。

计划的补救是改形状或筛掉已经赢的题，不是降门槛。形状已经对了（门 1），已经赢的
只有 11 道。剩下的缺口是「几乎只写 256」，筛不掉。

所以停在采集。`select_frontier.py` 的 `--min-speedup`、两道硬门脚本、逐题速度比
脚本都留下了，下一轮过门再用。

## 4. 评测口径改了

第十九阶段建议把头条从 k=4 解出数换成 pass@1 + pass@k 曲线。这一轮没有新权重，
正好改口径而不夹带模型对比。k=4 的 150 降为辅：它在 M 上饱和了，后面四轮
pass@1 都更高、解出都更低。速度继续只报共同题集上的逐题比；这一轮没有新模型，
那张表是空的。三个锚点（`27_SELU_` / `31_ELU` / `32_HardTanh`）没有新读数。

成功标准（共同题集中位 >1.05x，锚点 ≥0.80x）因为没训，不适用。

## 5. 顺带修的坑

- 大张量的 `get_inputs` 必须在 CUDA 上 `rand`。第一次验证在 CPU 上掷 6.4GB，
  GPU 空转，正确性阶段看起来像挂死。
- `ls dir/*_kernel.py | wc -l` 在 2000 个 NFS 文件上会卡住；改成 `os.listdir`。
- 计时时 `workers` 不能大于 GPU 数。`fast_verify.py --measure-time` 已经分两段
  （正确性可以超订、计时独占）；`grpo.py` 现在会把默认 8 个 worker 钳到 GPU 数，
  免得直接撞上 `VerifierPool` 的断言。
- 插入 `large_pointwise_activation` 时一度吃掉了 `long_elementwise_chain` 的
  `def` 行。测试现在要求两个 builder 都还在。

## 6. 下一步

速度差不是「没有更快的 kernel」。同一道题把 tile 从 256 改到 1024，就能从 0.56x
到 1.0x。差在策略几乎只发出例子里的那个数。

若再走速度这条路，要先让模型写出非 256 的 tile（改例子、在概念导读里写明
带宽受限时不要几百万个 block、或把温度/k 提到真能采到变异），然后用**同一套硬门**
再筛一次。不许拿这次未过门 2 的 250 道直接训。

第二套封存题集仍然不要开：它的激活是 8192 量级，测的不是这件事。
覆盖面仍然只剩修复循环那一个产出「模型本来写不出的解」的机制。

cuTile kernel 生成：评测、配方，以及还没解决的问题

在一套自建的 909 道题上量七个模型，并给出把解出数从 166 推到 634 的训练配方。

1　评测集 2　现有模型表现 3　训练配方 结语

1评测集：909 道题的独立尺子

这一章只回答一个问题：我们用什么尺子量“模型会不会写 cuTile”，以及凭什么相信这把尺子。 后面所有的模型对比、所有的涨跌，都是在这一套题、这一套判据下量出来的。 至于它和公开基准 KernelBench 是什么关系、差在哪里，放在本章最后的 1.9 对照着说。

1.1 题目从哪来

题目取自第二套封存题集（level 99 / 88 / 84，共 770 道）。这套题生成时就没有给任何模型看过， 也没有参与过任何训练或选数。评测用的是它们变异后的冻结副本，装成 level 60。

出处题数怎么来的
level 99400程序化 builder，全类别 curriculum
level 88250模型自撰图，经沙箱验证
level 84120程序化，专补激活 / 损失 / 归约

干净性是查过的，不是假设的。 按规范化哈希（去注释、去空行、压空格）比对了全部十三个已用 level（85、86、87、89、90–96 训练池，以及 97、98 第一套 held-out），结论是 770 道内部无重复、 与 3899 道已用任务无交集；生成时另外挡掉了约 1950 个逐字重复的候选。 这一点值得强调：换个随机种子不构成 held-out——第一套题集量过，那样做重复率高达 80%。

1.2 变异：让“背过原题”拿不到分

封存题集的原文一直留着不动，评测装的是按固定规则改写过的副本。不重新抽题、不加新算子词表、 不换骨干（conv / gemm / norm / pool / loss），只在已有的 forward 上改三件事： 近邻逐点算子置换、已知默认超参替换、维度重算。改完的哈希与 level 1、2、83–99 均无交集。

变异题数说明
图结构被改450逐点算子置换 335、外包一层 77、链序对调 15、去掉一层 13、复合 9
链长 ±1275加一层 198、减一层 77；只动逐点部分
超参被换161只替换已知默认字面量，如 negative_slope 0.01→0.02、eps 1e-5→1e-4

整套题可重复生成：taskgen/build_eval_suite.py 写出同一批文件， taskgen/test_eval_suite.py 校验构成。

1.3 两条轨：770 道延迟 + 139 道吞吐

909 = 770 + 139。这两条轨问的是不同的问题，读数拆开报，不折进同一个中位数。

轨题数形状量级看什么
延迟770 正确性量级（二维乘积 ≤ 2e7，中位约 3.2e6） 正确性 pass@1 / pass@4；对 torch.compile 的加速比
吞吐139 同图的大张量副本（1.0e9–1.3e9 元素） 只做成对吞吐比较，不对副本另开头条正确性

139 道吞吐副本全部来自 (batch_size, dim) 的 activation / elementwise 图 （elementwise 73、activation 66），图与母题完全相同，只放大形状。 softmax 族、norm、matmul、conv、pool、loss 不进吞吐轨—— 带跨 tile 归约或复杂索引的算子，在大张量上量到的是别的东西，混进来这个数就没法读了。

不规则那一档是刻意留的。模型很容易学会只在整除、对齐的形状上写对， 在不规则形状上崩掉或明显变慢是一个信号，而不是噪声。

1.5 通过判据：数值对，而且全是 cuTile

一个样本要算通过，两件事必须同时成立：

数值正确：与 PyTorch 参考实现逐元素比对。参考侧强制关掉 TF32 （allow_tf32=False、float32_matmul_precision="highest"）—— NGC 容器默认开 TF32，会让参考解自己就偏出 2e-2，反而把算得准的 cuTile matmul 判错。

纯度：完全用 cuTile 实现。三条静态检查同时通过：真的 import 了 cuda.tile 并有 @ct.kernel / ct.launch、没有残留 torch 计算算子、没有残留 torch.nn 计算层。 后两条在 KernelBench 上游只是 WARNING，这里提成硬性要求。宿主端脚手架 （nn.Module、torch.empty_like、.contiguous()）照常放行。

这条判据是这套评测最贵也最值的一部分：它让“看起来能跑”和“真的用 cuTile 写出来了”分开计分。 后面会看到，有的训练轮次涨的几乎全是纯度。

1.6 冻结协议

每个新模型都按同一套参数跑，否则不能横比。这套参数已经冻结，入口是 rl/compare_eval_suite.sh。

项值
Promptcutile_concepts 档；one-shot 示例与导读里的 tile 大小固定为 1024（见 1.7）
采样k=4，温度 1.0，top_p=0.95，top_k=40
落盘check_kernel=False：静态检查不合格的样本也全量留存，纯度门放到分析阶段
计时正确性筛完后在新容器里对 torch.compile 计时；180s 超时含 tileiras / ptxas 编译
表 Amax_tokens=32768，thinking 开
表 Bmax_tokens=8192，thinking 关

表 A 和表 B 不能横比，它们是两条协议。性能只在两个模型都解出的题上做成对比较， 不用各自解出集合上的中位数互相比——那个数会被“解出的是哪些题”带偏。

1.7 一个真实的例子：从输入到打分

抽第 92 题（92_ChainGELUAddBias_t4.py，elementwise 族，不规则形状）走一遍完整流程。 选它是因为四个模型在这一道题上刚好给出了三种不同的结局。

输入：题目

题目本身是一段标准的 PyTorch Model，一行 forward：

tasks/eval/level60/92_ChainGELUAddBias_t4.py 
import torch
import torch.nn as nn


class Model(nn.Module):
    """ChainGELUAddBias (tier 4, elementwise)"""

    def __init__(self):
        super(Model, self).__init__()
        pass

    def forward(self, x: torch.Tensor):
        return torch.nn.functional.gelu(x) + 1.5


batch_size = 3073
dim = 6144
def get_inputs():
    return [torch.rand(batch_size, dim)]


def get_init_inputs():
    return []

注意形状 3073 × 6144：这是被判成「不规则」的那一档。 3073 = 3×1024 + 1，刚好比 tile 大小的整数倍多出一个元素， 边界处理写错的实现会在这里露馅。母题原本是 4096 × 2048 的规整形状。

输入：实际发给模型的 prompt

发出去的完整 prompt 是 9,472 字符 / 247 行（约 2.4k token），由五部分拼成， 每道题只有最后的题目部分不同：

段落内容
任务说明用 cuTile kernel 替换 PyTorch 算子；可以自行决定替换哪些、是否融合
cuTile 编程模型导读cutile_concepts 档：tile 语义、@ct.kernel / ct.launch、tile 形状必须是编译期 2 的幂等约束；以及 tile 该取多大
one-shot 示例一个向量加法的完整实现，含 host 端 launcher 和 ModelNew；TILE_SIZE = 1024 就写在这里
题目上面那段 Model 源码，原样贴入
输出要求fp32 精度；命名为 ModelNew；只输出代码块

导读部分的开头是这样的——注意它明确写了「这不是 Triton」，因为模型最容易犯的错就是把 Triton 的 API 搬过来：

cuTile is NVIDIA's tile-based GPU programming model, exposed in Python as the
`cuda.tile` package (conventionally imported as `ct`). It is *not* Triton, CUDA C++,
or CuTe/CUTLASS, and none of their APIs exist here.

Where a SIMT kernel reasons about individual threads, a cuTile kernel reasons about
whole **tiles**: you load a tile of many elements, operate on the entire tile at once,
and store it back. ...

- **Tile shapes must be compile-time constants, and each dimension must be a power of two.**
  A shape like `(96,)` or a shape read from `x.shape` at runtime will not compile.

文档档位是刻意选的。完整 API 参考约 14.9k token，会占掉整条序列的 91%； cutile_concepts 档只有约 2.4k token，是训练和评测都负担得起的档位。

tile 大小：协议里最不起眼、却最贵的一行

协议写着「TILE_SIZE = 1024」，但 prompt 里没有任何一句话命令模型用 1024。 它是通过两处「示范」传达的。一处是导读里的一段话： 

A pointwise kernel over a large array should use a large power-of-two tile
(1024 or more). A 256-element tile on a billion-element input launches millions
of blocks; that launch overhead is pure loss on a bandwidth-bound kernel. Tile
dimensions must still be compile-time powers of two.

另一处是 one-shot 示例的第一行常量——模型照抄的其实主要是这个：

import cuda.tile as ct

TILE_SIZE = 1024


@ct.kernel
def add_kernel(a, b, out):
    # One tile block per TILE_SIZE-element chunk of the flattened arrays.
    i = ct.bid(0)
    # PaddingMode.ZERO zero-fills the tail tile when the length is not a
    # multiple of TILE_SIZE; out-of-bounds stores are discarded automatically.
    a_tile = ct.load(a, index=(i,), shape=(TILE_SIZE,), padding_mode=ct.PaddingMode.ZERO)
    b_tile = ct.load(b, index=(i,), shape=(TILE_SIZE,), padding_mode=ct.PaddingMode.ZERO)
    ct.store(out, index=(i,), tile=a_tile + b_tile)

为什么要把这件事单独拎出来说：这一个常量值本身就抵得上一轮训练。 示例原本写的是 256。把它改成 1024、其余一律不动、权重一个字节都没改之后重测： 60 个 kernel 里 56 个写了 1024、0 个写 256， 几道逐点激活锚点对 torch.compile 从约 0.55x 跳到 1.02–1.05x， 大张量 GELU 从 0.75x 到 1.12x。

原因不难理解：十亿元素的逐点核用 256 的 tile，要启动几百万个 block， 在带宽受限的算子上这部分开销是纯亏。但模型不会自己推断这一点，它照抄示例。 这也是为什么协议必须把 tile 大小连同 prompt 一起冻结—— 不冻的话，换个示例就能让分数动一大截，那量到的就不是模型能力了。

输出：同一道题上的三种结局

每个模型采 4 个样本。这一道题上的逐样本结果：

模型通过四个样本分别发生了什么
Next0 / 4 全部编译失败：3 个 rank 不匹配，1 个 tile 形状非法
GL2 / 4 2 个通过；2 个纯度失败——GELU 仍然调 torch
GL-A2 / 4 2 个通过；2 个编造了不存在的 API（ct.erf、ct.gelu）
Next-Q4 / 4 全部通过，对 torch.compile 加速 1.92x–2.21x

这就是判据在做的事。 三种失败各自长什么样，值得看一眼原始代码。

失败形态一：host 端 launcher 写错

未训练的 Next 把输入展平了，却忘了把输出也展平，于是 kernel 收到一个 2 维数组、 却按 1 维索引去写：

runs/base_l60/level_60_problem_92_sample_0_kernel.py（节选） 
    x_flat = x.view(-1)
    n = x_flat.numel()
    grid = (ct.cdiv(n, TILE_SIZE), 1, 1)
    ct.launch(torch.cuda.current_stream(), grid, gelu_add_bias_kernel, (x_flat, out))

最后一个参数应当是 out.view(-1)。 判定：TileTypeError: Index size 1 does not match the array rank 2 → 失败（exec）。 kernel 主体其实写对了，GELU 的 tanh 近似、边界 padding 都没问题——错在最后一行。

失败形态二：数值全对，但不是 cuTile

未训练的 GL 只把「+1.5」写成了 kernel，GELU 留给了 F.gelu。 这份实现数值完全正确、也能跑，标准 pass@k 会给它记一分：

runs/GL_l60/level_60_problem_92_sample_2_kernel.py（节选） 
import torch.nn.functional as F

@ct.kernel
def add_bias_kernel(x, out):
    i = ct.bid(0)
    t = ct.load(x, index=(i,), shape=(TILE_SIZE,), padding_mode=ct.PaddingMode.ZERO)
    ct.store(out, index=(i,), tile=t + 1.5)

class ModelNew(nn.Module):
    def forward(self, x):
        x = F.gelu(x)
        return add_bias(x)

真正的计算（GELU）还留在 torch 里，kernel 只做了那个加法。 判定：Uses torch.nn.functional op: F.gelu → 失败（purity）。 这正是 1.5 里说的那条判据在起作用——不这样判，这份答案会让分数虚高。

通过的样子

训练完成的 Next-Q 在这道题上四个样本全通过。这是其中之一，逐字原文：

runs/Q_l60/level_60_problem_92_sample_0_kernel.py 
import torch
import torch.nn as nn
import cuda.tile as ct

# Tile size should be a power of 2, using 1024 as it's a good balance
TILE_SIZE = 1024

@ct.kernel
def gelu_add_bias_kernel(x, out):
    i = ct.bid(0)

    # Load tile with padding for boundary handling
    x_tile = ct.load(x, index=(i,), shape=(TILE_SIZE,), padding_mode=ct.PaddingMode.ZERO)

    # Apply GELU approximation: 0.5 * x * (1 + tanh(sqrt(2/π) * (x + 0.044715 * x^3)))
    # For better performance, we'll use the efficient approximation
    x_squared = x_tile * x_tile
    x_cubed = x_squared * x_tile

    # GELU approximation coefficients
    sqrt_2_over_pi = 0.7978845608028654  # sqrt(2/π)
    coef = 0.044715

    # Compute GELU: 0.5 * x * (1 + tanh(sqrt(2/π) * (x + 0.044715 * x^3)))
    inner = sqrt_2_over_pi * (x_tile + coef * x_cubed)
    tanh_inner = ct.tanh(inner)
    gelu_result = 0.5 * x_tile * (1.0 + tanh_inner)

    # Add bias of 1.5
    result = gelu_result + 1.5

    # Store result (out-of-bounds writes are automatically discarded)
    ct.store(out, index=(i,), tile=result)


def cutile_gelu_add_bias(x: torch.Tensor) -> torch.Tensor:
    """Host-side launcher for GELU + bias operation."""
    x = x.contiguous()
    out = torch.empty_like(x)

    # Flatten input for tile-based processing
    x_flat = x.view(-1)
    out_flat = out.view(-1)
    n = x_flat.numel()

    # Calculate grid size
    grid = (ct.cdiv(n, TILE_SIZE), 1, 1)

    # Launch kernel
    ct.launch(torch.cuda.current_stream(), grid, gelu_add_bias_kernel, (x_flat, out_flat))
    return out


class ModelNew(nn.Module):
    """ChainGELUAddBias (tier 4, elementwise) - optimized with cuTile"""

    def __init__(self):
        super(ModelNew, self).__init__()
        pass

    def forward(self, x: torch.Tensor):
        return cutile_gelu_add_bias(x)

判定：通过，对 torch.compile 2.21x。

三件事让它成立：GELU 用 tanh 近似自己算出来而不是找一个不存在的 ct.gelu； 输入输出都展平；PaddingMode.ZERO 配合越界写丢弃， 让 3073×6144 这个不能被 1024 整除的形状不需要任何特判就正确。 最后这点正是不规则形状那一档要考的东西。

1.8 这套尺子量不到什么

两个缺口是已知的，写在这里免得被误读：

损失函数只有 5 道，基本没有判别力。 不是配置失误：损失族的算子面只有 7 个算子、 形状阶梯又短，组合空间已经被训练集吃干。要真正覆盖损失，得先扩充损失算子面本身。

1.9 和 KernelBench 的关系与区别

项目起步时用的就是 KernelBench：Level 1（100 道单算子）+ Level 2（100 道融合链），共 200 道题。 现在这 200 道题只留作历史对照，头条读数换成了自建的 909 道。

需要先说清楚：我们没有抛弃 KernelBench 的工程。题目格式仍是它的 （Model / get_inputs / get_init_inputs）， cuTile backend 是接进它的 backend 抽象里的，加载、prompt 组装、评测入口都沿用它的代码。 换掉的是题目本身、判据和性能基线这三样。

KernelBench（Level 1+2）本项目评测集（level 60）
题量 200 909（770 延迟 + 139 吞吐）
题目来源 公开仓库，可被搜索到 程序化 builder + 模型自撰，从未公开发布
污染风险 题面与参考解大概率在预训练语料里 与十三个已用 level 逐一做哈希比对，确认无交集
通过判据 数值正确即可；允许只替换一部分算子，纯度检查是 WARNING 级 数值正确 且 完全用 cuTile；三条纯度检查提为硬性
性能基线 默认对 eager PyTorch 一律对 torch.compile（inductor）
形状 原题给定 按 id 分成常见 / 不规则两档，187 道刻意不整除、不对齐
吞吐 无此概念 139 道大张量副本单独成轨，与延迟分开报
采样协议 随实验而变 冻结：prompt 档位、tile 大小、k、温度、top_p / top_k 全部固定
计时吞吐量 每样本重开进程 + 100 次性能计时，约 6 样本/分钟 批量校验、20 次性能计时；正确性与计时分两个阶段

下面三条是这几处差别里最要紧的，各自都有踩过坑的来由。

差别一：判据——“正确”不等于“写了 cuTile”

KernelBench 允许模型只替换一部分算子，于是一个通篇 torch.matmul、 一行 cuTile 都没有的 ModelNew，照样能拿到“正确 + 约 1.0x 加速”。 要量的是 cuTile 生成能力，这种答案就必须判失败。1.5 会给出完整判据， 1.7 有一份真实的、数值全对但被判纯度失败的代码。

差别二：性能基线——对 eager 比是在跟一个偏弱的对手比

这是项目中代价最大的一次口径修正。前十二轮所有加速比都是对 eager 量的， 而基准里一半是融合链，我们在那里的胜绩几乎全部来自“PyTorch 会物化中间结果”—— 恰恰是 torch.compile 免费消除的那部分。

换成 compile 基线重测后，模型排序直接翻转：eager 口径下 L 胜 K（60 比 49 道更快）， compile 口径下 K 胜 L（45 比 41）。“中位追平 PyTorch”也不成立了，实际是 0.92x。 更糟的是，当时的强化学习奖励函数用的正是 eager 口径—— 我们在训练模型去赢一个偏弱的对手。

教训写进了协议：基线的选择本身就是一个可以骗自己的旋钮。 该问的是“用户真正会用什么”，而不是“哪个跑得出好看的数”。

差别三：这 200 道题已经被我们自己用旧了

每一轮训练完都在这 200 道题上挑“留哪个 checkpoint”，前后挑了六次。 挑到第六次，它衡量的就不只是模型能力，还包含了我们照着它做的调优。 一把用来做过六轮选型的尺子，不能再当作对外汇报的尺子—— 这也是为什么新题集在生成时就封存，且规定只按冻结协议跑、不参与选型。

2.2 表 A 头条（开 thinking，32K）

k=4 采样。pass@4 = 四次里至少一次通过的题目占比，括号里是题数； pass@1 是逐样本通过率。两条轨分开报，不折进同一个数。

吞吐轨的通过率普遍高于延迟轨，不是因为大张量更容易， 而是因为这 139 道全部是 activation / elementwise——恰好是所有模型都最擅长的两族 （见 2.3）。所以吞吐轨的读数只适合模型之间横比，不能拿来代表整体能力。

三件事值得单独指出来。

公开模型之间的差距，小于「训没训过」的差距。 GL 580、G4t 569 挨得很近，Q38 366 掉一档；而同一个 Next 权重，训练前 166、训练后 634， 差了 3.8 倍。这说明这套题考的不是通用代码能力，是一个特定 DSL 的熟练度。

Next 这个基座在未训练时是最差的（166），训练后是最好的（634）。 它是唯一一个专门的代码模型，却在 cuTile 上垫底—— 更说明 cuTile 不在任何一家的预训练语料里，代码能力不能自动迁移过来。

「解出」和 pass@1 的差距就是可用性的差距。 GL 解出 580 道，也就是四次里至少对一次的比例有 75.3%，但 pass@1 只有 51.5%： 它「会写」，但不稳定。真实使用是采一次就用，这 24 个百分点正是训练要收窄的东西。

2.3 能力沿算子族断层分布

按算子族拆开看，会发现模型不是「均匀地差」，而是在某几类上整体塌陷：

逐点算子人人都会，卷积和池化才是分水岭。 activation 这一族最好和最差只差 11 道（141 对 130）， 而 conv 从 23 到 174、pool 从 2 到 64。原因不在算法难度，在能不能跳出 「一个 block 管一维 tile」这个最简单的映射：激活函数可以， 卷积、池化要处理多维索引、跨 tile 归约和边界，模型就塌了。

Q38 的 conv 只有 23/209，几乎全军覆没，这也是它总分掉一档的主要来源。 未训练的 Next 在 pool 上只解出 2 / 75。

2.4 失败形态：一半以上不是「算错」

每个模型采 3636 个样本（909 × 4）。把没通过的样本按失败阶段拆开，能看出问题出在哪一层。 下图是训练前后的同一个基座（G4t 通过 1917 个样本，未做阶段拆分）：

纯度失败是最大的单一失败类别：GL 有 970 个样本数值算对了、却因为把活留给 torch 而不算通过 （1.7 里那份 F.gelu 的代码就是典型）。 这意味着按标准 pass@k 报，这些模型的分数会明显虚高。

还有一类失败与 cuTile 无关：Q38 有约一半样本在 32K 上限内没能写完 thinking， 根本没输出代码。这也是它 tile 统计不能和别人横比的原因。

2.5 不规则形状：没有出现整片崩塌

不规则档的解出率普遍只比常见档低几个百分点， 没有出现「整除就会、不整除就崩」的断崖。 这说明 PaddingMode.ZERO 加越界写丢弃这个写法，模型基本吃进去了—— 1.7 那个 3073×6144 的例子就是证据。这一档是设来抓问题的，这次没抓到，是好消息。

2.6 性能

性能必须分轨读：延迟轨（770 道小张量）和吞吐轨（139 道大张量）量的是两件事， 折进同一个中位数就没法解释了。参考实现一律是 torch.compile， 加速比 = 参考的 ref_ms ÷ 生成 kernel 的 kernel_ms， 每道题取该模型通过样本里最快的一个。

延迟轨：题目太小，这一档量的主要是调度开销

这些倍数看着很漂亮，但不能当作「我们比 inductor 快两倍」来读。 延迟轨的题按正确性量级出，中位只有约 3.2e6 个元素（12.6 MB）： 生成 kernel 的中位耗时约 34 µs，参考约 75 µs。 在这个尺度上，差距主要来自参考实现启动了几个 kernel、有多少调度开销， 而不是算得多好。这正是本项目不把延迟轨的绝对加速比当头条的原因。

注意图 2.6 里两组柱的反差：「自己解出集」和「共同 101 题」差了一倍 （例如 GL 是 2.33x 对 5.15x）。同一批 kernel、同一次计时，只因为统计的题目集合不同， 读数就能差这么多——这就是为什么绝不能拿各模型自己集合上的中位数互相排名。 共同 101 题那一组才是同题同比，而它显示七个模型挤在 4.35x–5.18x， 未训练的 Next 也在其中：这一档拉不开差距。

吞吐轨：这一档才是真实的带宽比较

139 道副本每道约 1.2e9 个元素（单个张量 4.7 GB），完全是带宽受限， 调度开销可以忽略。这一档七个模型的中位加速比挤在 1.13x–1.19x（共同 47 题）， 彼此没有差别。换算成实际带宽更直观：

GB200 单卡 HBM 标称带宽约 8 TB/s，所以生成的 kernel 跑在约七成峰值上， 比 inductor 高约 22%。GL 是 5700 / 4784 GB/s，GL-A 是 5889 / 4754 GB/s， 三个模型几乎一样。

这是一个真实但不属于模型的优势。 大张量逐点算子只要写成 「一维展平 + 大 tile + padding」这一种形态就能拿到这个带宽， 而这个形态在 prompt 的 one-shot 示例里就给了。所以连未训练的 Next 都在同一档—— 快的是 cuTile，不是哪个模型更会调优。 图 2.9 还显示，即便如此仍有约两成的题慢于 torch.compile， GL 更是有三成：这些是逐点之外、或写法退化的样本。

2.8 小结

把这一章压成三句话：

一、cuTile 不是「换个语法的 CUDA」，公开模型不会写。 最强的公开模型 pass@1 51.5%，专门的代码模型未训练时只有 8.5%。

二、缺口是可以补上的，而且补得动。 同一权重 166 → 634， 在 conv、pool 这些整族塌陷的地方涨得最多。

三、涨的是正确性，不是性能。 生成的 cuTile kernel 在大张量上确实比 torch.compile 快约两成（5824 对 4754 GB/s），但七个模型不分伯仲—— 那是 cuTile 本身的优势，不是训练买来的。 让模型学会「写得更快」目前还没有拿到可信的提升，这是下一阶段要投入的地方。

3配方：166 → 634 是怎么做到的

这一章讲方法。训练语料全部自产：程序化生成的任务 + 模型自己的通过解， 没有用任何人写的参考实现。官方文档只出现在 prompt 里。 唯一的裁判是验证器——cuTile 编译器加上与 PyTorch 的数值比对， 跟评测用的是同一份 verify/worker.py，所以训练里的「对」和评测里的「对」 不可能漂移。

读数说明：这一章的解出数是当年的尺子（KernelBench Level 1+2 共 200 道）， 因为每一关的对照都是在那上面做的。第 2 章的 909 道题是后来才建的， 两套数不能互相换算。

3.1 链条与每一关的增量

十九轮下来一共改过十几次权重，下面是留在主线上的九个 checkpoint。 颜色是干预类型：能看出 SFT 类的两跳最大，RL 类的连续但递减。

有几件事这张图直接说明了：

第一次 GRPO 是空转。 E 那一轮花了 6.7 GPU 小时，解出从 52 掉到 51， 而同期一轮 SFT 约 35 分钟换来 +1pp。事后归因有四条：可训练参数只有 34M（0.04%）、 prompt 长达 14.9k token 让一步训练占掉每轮 954 秒里的 745 秒、学习率 1e-6、 以及最致命的一条——采样器从不刷新，rollout 一直来自最初服务的模型， 而 old logprob 取的是当前模型，重要性比值恒等于 1，修正从未真正发生。

同样的 GRPO，修好之后连续四轮有效（108 → 127 → 134 → 144 → 150）， 而且叠在自蒸馏之上增益没有被吃掉：F→I 是 +19，H→J 也是 +19。

但边际收益在衰减：+19 → +7 → +10 → +6，之后转负。 M 的 150 道连续四轮没有被超过。

解出数从 51 跳到 84 的那一关（图 3.1 里的 F），改动只有一件事： 训练时不再把 14.9k token 的完整 API 参考塞进 prompt，换成 2.4k token 的概念导读。

原因很朴素：文档占了每条训练序列的 91%，梯度预算几乎全花在复现一段所有样本都一样的前缀上。 换成短档之后，同样的显存能训 7 倍的样本量。

自蒸馏更便宜（1534 条样本、24 分钟训练）也更有效，而且 pass@1 / pass@4 / pass@16 三个口径同时涨——没有拿覆盖面换可靠性。

最值钱的发现是两条臂互补。 自蒸馏把卷积从 31 推到 50， 但池化、归约、损失一道都没多解；GRPO 卷积只 +7，却把池化 1→3、归约 3→5 推动了。 机理清楚：自蒸馏的数据分布由「模型已经能答对什么」决定，弱类别没有正样本可蒸； GRPO 的 frontier 按「有时对」筛，弱类别偶尔蒙对一次就进训练集。

3.4 让 RL 真正生效的三处修正

三轮 GRPO 各自解决了一个具体缺陷，都不是调超参：

轮次发现的问题改动增量
K（十一） frontier 表里根本没有 activation 和 loss——任务生成器没有这两族的 builder，而它们占基准 17.5% 按 torch API 面枚举补 24 个激活 + 7 个损失；select_frontier.py 加类别配额 +7
L（十二） 「数值错」是一个笼统的 0 分档，编译不过和差 1e-3 同分 按误差量级分级给分 +10
M（十四） 剩余未解题里 52% 是数值正确但链尾留了个 torch 激活 纯度失败从恒定 0 改成按剩余算子数在 0.18→0.04 插值（严格低于「编译不过」的 0.20，保证甩回 PyTorch 永远不划算）；任务生成加「锚 + 链尾激活」形态 +6

M 这一关把 pass@1 首次推过一半（44.6% → 51.6%）。 注意第三行的设计：奖励刻度的上下界是构造出来的，不是调出来的—— 任何「纯的尝试」得分都不低于任何「不纯的尝试」。

3.5 四个否定结果

这些占了大约三分之一的机时，写在这里是因为它们决定了下一步不该往哪投。

做过的事结果为什么

3.8 五个能骗自己的旋钮

这一节是全项目最值得留下的部分：每一条都是一次自我欺骗被当场抓住， 而且都已经变成了代码里的防呆。

一、基线。 十二轮没人质疑过 eager PyTorch，而它恰好在我们最爱宣称胜绩的 融合链上最弱。换成 torch.compile 后「中位追平 PyTorch」变成 0.92x， 两个模型的排序还翻转了。

二、等预算对照。 多轮方法必须和同等采样预算的单轮比， 否则「反馈有用」和「多采几次」分不开。

三、判据本身可能有 bug。 曾用 compiled and not correct 判定 「能跑但数值错」，报出 92%。但 compiled 只表示模块导入成功， 而 cuTile 是首次 launch 才 JIT——所有编译错误都被算成了数值错。 真实的最大项是纯度失败（52%），完全是另一回事，靶子因此瞄错了一轮。

四、贴着天花板的训练指标不能用来排除失败模式。 训练侧纯度率 0.971 纹丝不动，被我读成「没有风险」，基准上却丢了 9 道。

五、构成效应。 两个模型解出的题不是同一批， 拿各自集合上的中位数比较，涨跌全是构成变化（2.6 里图 2.6 就是这个现象的直接证据）。 现在的纪律是：性能一律在共同题集上逐题比。

贯穿全程的一条观察：后期每一轮的失败都不是方法不对，而是训练分布和基准分布对不上—— 类别构成（十一）、失败形态（十四）、性能区间（十六）、发出的 tile 尺寸（二十）， 四次都是同一个形状的问题。自产语料的代价就在这里：任务是我们造的， 它的分布就是我们对「什么是难的」的假设，而那个假设一直偏乐观。

结语：这项工作留下了什么

cuTile 是一个新 DSL。新 DSL 的采用成本里，很大一块是「没人会写、也没有语料可学」—— 模型帮不上忙，工程师就得手写；手写的人少，语料就更少。这项工作针对的正是这个循环。 三章看下来，留下的东西可以分成四份。

一把可信的尺子

909 道题、冻结协议、判据是「数值对且完全用 cuTile」。它的价值不在题目本身， 而在于此后任何一个模型、任何一次权重改动，都能用同一把尺子在约 3 小时内量出可比的读数， 而且这个读数经得起追问：题目从未公开、与十三个已用题库逐一哈希比对无交集、 性能一律对 torch.compile 而不是对更弱的 eager、只在共同题集上做成对比较。

这套东西本身就是可复用资产。第 2 章里七个模型的横向读数，是它上线后的第一批产出。

一条被两个基座验证过的配方

同一份权重从解出 166 道到 634 道，pass@1 从 8.5% 到 69.4%。更重要的是它不是一次性的： 同一条配方搬到另一个完全不同的基座（Muse Glimmer，dense 30B）上， 一轮就把 580 推到 619，pass@1、pass@4、吞吐三个口径同时涨。

整条配方不依赖任何人写的 cuTile 参考实现。 训练数据是程序化生成的任务加上模型自己的通过解，裁判是编译器和数值比对。 这意味着它可以随 cuTile 的演进自动续期——DSL 增加了新算子面， 补上任务生成器就能再跑一轮，不需要先攒一批人写的示例。

成本也是清楚的：一轮完整迭代约 12 GPU·小时，单机 4 卡约 3 小时墙钟，其中训练只占五分之一。

一批负面结果

四个否定结论（纯度上限、性能专项 RL、性能训练集重筛、修复循环当推理手段） 加上五个「能骗自己的旋钮」，大约花掉三分之一的机时。 它们的价值是让下一笔投入不必重复购买同样的教训： 基线选 eager 会让排序翻转、多轮方法必须和等预算单轮比、 贴着天花板的训练指标不能用来排除失败模式、涨跌可能只是题目构成变了。 这些现在都已经变成代码里的防呆，而不是留在某个人的记忆里。

对 cuTile 本身的一个读数

顺带量到一件与模型无关的事：在 139 道十亿元素的逐点算子上， 生成的 cuTile kernel 中位达到 5824 GB/s，而 torch.compile 是 4754 GB/s， 约为 GB200 标称带宽的七成。这个差距七个模型几乎一样—— 说明它来自 cuTile 这条路径本身，而不是某个模型更会调优。 对「cuTile 值不值得推」这个问题，这是一个独立于本项目的正面证据。

还欠着的

报告标题里那句「还没解决的问题」不是修辞。性能这条线目前是空的： 正确性训练不搬动性能，专项尝试两次都没过自己设的门，而诊断已经很具体—— 合成任务池里缺「稳定解出、比参考慢、还追得上」的那段区间，这是任务生成的问题， 不是奖励函数的问题。此外池化和卷积仍有明显缺口，cuTile API 面的泛化还没有题集能量。

换句话说：「能不能写对」这个问题已经基本回答了，「能不能写得快」还没有开始回答。 前者证明了这套方法体系走得通，后者知道卡在哪、也知道该从任务生成而不是训练算法入手。 这是下一阶段值得投入的位置。

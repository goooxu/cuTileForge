# 六模型 1+1+1+1 自适应搜索

同一个模型、同一道题、同样四次调用。control 是四次独立同 prompt；adaptive
每次生成后先执行、验证和计时，再把当前最值得继续的代码与反馈交给下一轮：

1. 原冻结 prompt；
2. 失败则修复，通过则尝试单核融合；
3. 失败则修复，通过则换一种多阶段分解；
4. 失败则修复，通过则按 `kernel_ms` 改 tile / grid。

没有训练，没有模型路由。通过仍要求数值正确且全部计算在 cuTile。速度取四个
通过候选里最低的 `kernel_ms`，不拿 compile `su` 选候选。

## 1. 协议

- 开发题来自冻结的 level 64：64 matmul + 64 conv；不含 level 60 或 heldout。
- 先按 task hash 固定 16 + 16 道作筛选；模型输出生成前 manifest 已冻结。
- GL-E、GL、Next-Q、Next、G4t、Q38 都按各自 32K 表 A 类协议生成。
- Q38 后续轮次要携带完整上一份代码，服务 context 上限设为 98304；输出上限仍
  是 32768。
- 当前 nightly 的 SM100 FlashInfer TRT-LLM BF16 MoE warmup 会 illegal access。
  Next / Next-Q 的 control 和 adaptive 两边都固定 `--moe-backend triton`。

筛选门：adaptive p@4 不低于 control，并且多解至少 1 道或共同题最快
`kernel_ms` ≥1.05x。完整 128 题把覆盖门改成多解至少 2 道。

## 2. 32 题筛选

表里的 p@1：control 是四次独立样本的通过率；adaptive 是 Round 0 的单发通过率。

| 模型 | control p@1 / p@4 | adaptive p@1 / p@4 | 解出 control→adaptive | 最快 `kernel_ms` | 门 |
| --- | ---: | ---: | ---: | ---: | --- |
| GL-E | 80.5% / 96.9% | 90.6% / 96.9% | 31→31 | 0.925x | 未过 |
| GL | 55.5% / 87.5% | 46.9% / 93.8% | 28→30 | 0.491x | 覆盖过 |
| Next-Q | 95.3% / 96.9% | 96.9% / 100.0% | 31→32 | 1.000x | 覆盖过 |
| Next | 33.6% / 53.1% | 31.2% / 50.0% | 17→16 | 0.992x | 未过 |
| G4t | 66.4% / 87.5% | 56.2% / 78.1% | 28→25 | 0.997x | 未过 |
| Q38 | 21.1% / 56.2% | 28.1% / 81.2% | 18→26 | **1.061x** | 覆盖、速度都过 |

GL、Next-Q、Q38 进入完整 128 题。其余不扩。

## 3. 完整 128 题

| 模型 | control p@1 / p@4 | adaptive p@1 / p@4 | 解出 control→adaptive | 最快 `kernel_ms` | 门 |
| --- | ---: | ---: | ---: | ---: | --- |
| GL | 46.9% / 78.9% | 49.2% / 85.9% | 101→**110** | 0.970x | 覆盖过 |
| Next-Q | 93.4% / 96.9% | 93.8% / 96.1% | 124→123 | 1.000x | 未过 |
| Q38 | 17.4% / 46.9% | 20.3% / **68.0%** | 60→**87** | **1.054x** | 覆盖、速度都过 |

分族：

| 模型 | matmul 解出 control→adaptive | matmul `kernel_ms` | conv 解出 control→adaptive | conv `kernel_ms` |
| --- | ---: | ---: | ---: | ---: |
| GL | 52→55 | 0.439x | 49→55 | **1.091x** |
| Next-Q | 64→64 | 1.000x | 60→59 | 1.015x |
| Q38 | 37→**61** | **1.054x** | 23→26 | **1.083x** |

Q38 是清楚的正结果：相同四发预算下多解 **27/128**，共同题最快 kernel 中位
1.054x。matmul 从 57.8% p@4 到 95.3%，conv 从 35.9% 到 40.6%。GL 也多解
9 道，但整体更慢，尤其 matmul 只有 0.439x；自适应 prompt 在这里主要买正确性。
Next-Q 已接近饱和，反馈没有余量，反而少 1 道。

## 4. 结论

- **反馈适合补能力缺口，不是普遍的速度优化器。** Q38 和未训练 GL 的覆盖明显涨；
  GL-E、Next-Q 这类高覆盖模型没有稳定收益。
- **独立 k=4 本身是很强的速度搜索。** 后三轮围绕当前通过解重写，会收窄代码分布；
  GL 的 matmul 因此比四次独立采样慢得多。
- 最终选中代码的静态中位均是 1 个 `ct.launch` site；Q38 adaptive 有 2 个
  `@ct.kernel` 定义（control 是 1 个）。这是静态定义数，不等于运行时 launch 数。
- 这是新的开发协议，不能替换或横比现有表 A / B。是否在 909 题上单开正式自适应表，
  需要另行决定。

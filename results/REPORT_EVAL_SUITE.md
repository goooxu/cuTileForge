# 独立评测集：两张协议表

同一套题（level 60：770 延迟 + 139 吞吐），一次对 `torch.compile` 计时。
通过 = 数值对且全是 cuTile。冻结采样：`cutile_concepts` + `TILE_SIZE=1024`，
k=4，温度 1.0。没有训练。

**两张表不能横比。** 表 A 是开 thinking、`max_tokens=32768`。表 B 是关
thinking、`max_tokens=8192`。旧两轨和 KernelBench 200 题头条也不要混进来。

**表内名称**（脚本和 `runs/` 目录仍用短 tag）：

| 表内 | tag | 是什么 |
| --- | --- | --- |
| Next | `base` | Qwen3-Coder-Next，未在本项目训练 |
| Next-M | `M` | 拒绝采样 SFT → 丢掉长文档 → 自蒸馏 → GRPO |
| Next-Q | `Q` | 在 Next-M 的通过解上第二次自蒸馏 |
| Q38 / Q38nt | `Q38` / `Q38nt` | Qwen3.8-27B，开 / 关 thinking |
| G4 / G4t | `G4` / `G4t` | Gemma-4-31B-it，关 / 开 thinking |
| GL | `GL` | Muse Glimmer 30B |

**结论先说**

1. **表 A（32K，开 thinking）**：Next-Q 与 Next-M 打平（634 / 629）。GL（Muse Glimmer，
   `reasoning_strength=xhigh`）580/770，在 Q38（366）和 Next-M / Next-Q 之间。conv 146/209
   （Q38 只有 23）。激活 **141/150**，高于 Next-M / Next-Q。
2. **表 B（8K，关 thinking）**：Next-Q 与 Next-M 仍打平（634 / 632）。Q38nt 398/770。
   G4（官方默认关 thinking）354/770，低于 Q38nt，远低于 Next-M / Next-Q。conv 57/209，
   激活 111/150。loss 5/5。
3. 两张表里延迟和吞吐做成对都没有拉开。延迟中位 ms 和吞吐中位加速比不要横比。

# 两张表之间

不能把表 A 的中位数和表 B 折在一起。只在 Q38 自己身上看开关：

| | 表 A（think，32K） | 表 B（off，8K） |
| --- | ---: | ---: |
| 延迟 | 366/770 | 398/770 |
| 吞吐 | **121/139** | 110/139 |
| conv | 23/209 | **75/209** |
| activation | **130/150** | 115/150 |

关 thinking 换来 conv，丢掉激活和吞吐。两边都远低于同表的 Next-M / Next-Q（conv 174 / 177）。

32768 关 thinking 试跑（397/770，102/139）归档在 `runs/archive_q38nt_32768/`。
头条和表 B 同量级，薄尾巴不是瓶颈，不单开第三张表。那一轮也是温度 1.0 重采，
和表 B 的解出集合只重叠 285 道，不要把集合差当成上限效应。

# 这意味着什么

- 两条协议上 **Next-Q 与 Next-M 都打平**，延迟和吞吐都没有拉开。
- Q38 开 thinking 停在 366/770，洞在 conv。关 thinking 抬到 398，仍不是 Next-M / Next-Q。
- G4 只进表 B：354/770，低于 Q38nt，洞同样在 conv / matmul。没有开 thinking。
- 下次新模型按 [tasks/eval/EVAL.md](../tasks/eval/EVAL.md) 的对应那张表跑，
  不要跨表填数。

## 为什么要第二套

第一套（`HELDOUT.md`，level 97/98）生成于第九阶段，**那时激活和损失的 builder 还不存在**，
`anchor_with_tail`（链尾激活）也不存在。所以它里面没有一道独立的激活题、没有损失题、
也没有链尾形态——**恰好覆盖不到第十一到十七阶段做的全部改动**。

第一套还在第十一阶段开封过一次（结论：没有过拟合迹象）。此后 dev 200 又用于六轮选型决策。
常设尺子改走独立评测集，见 [eval/EVAL.md](eval/EVAL.md)。

## 排除范围

按规范化哈希（去注释、去空行、压空格）排除了**全部十三个已用 level**：
85, 86, 87, 89, 90-96（训练池，3899 道去重后）以及 97, 98（第一套 held-out）。

```bash
python3 taskgen/check_holdout.py --holdout 99,88,84 \
    --train 85,86,87,89,90,91,92,93,94,95,96,97,98
```

结论 `clean`：770 道内部无重复，与 3899 道已用任务无交集。生成时挡掉了约 1950 个逐字重复的
候选——**换种子不构成 held-out**，这一点在第一套的文档里已经量过（80% 重复率）。

## 已知的两个缺口

**损失函数只有 5 道。** 不是配置失误——`--only-categories loss,...` 也只挤出 3 道。
原因是 `LOSS_OPS` 只有 7 个算子、形状阶梯又短，**这个族的组合空间已经被训练集吃干了**
（level 87 的 frontier 里有 45 道 loss，SFT 集里有 92 条）。要真正覆盖损失，得先扩充
损失算子面（加权、margin、不同 rank），那是任务生成的改进，不是这里能补的。
所以**这套题集对损失族基本无判别力**，dev 上那 6 道仍然只能靠 dev 自己说话。

**仍然测不了 cuTile API 面的泛化。** 用的 torch 算子词表都是训练期见过的，新的只是形状和
组合。要测 API 泛化需要词表本身没见过的题集，目前没有。
